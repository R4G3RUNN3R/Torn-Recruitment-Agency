# Recruitment Agency v4.3 Google Sheets Global Intelligence Design

## Goal

Add an optional shared intelligence layer to Recruitment Agency using a private Google Sheet as the global data store and a Google Apps Script web app as the public read/write API.

Any Recruitment Agency user who legitimately obtains Torn player data through the script can contribute a sanitized observation. Other users can then retrieve that player's previous observations and compare current data against historical shared observations.

The global layer is supplemental. Fresh direct Torn API data and the user's current local Scout snapshot remain authoritative over older shared observations.

## Scope

v4.3 Global Intelligence includes:

- one private Google Sheet with `Players`, `Observations`, and `Meta` tabs;
- one Google Apps Script web app acting as the only public read/write interface;
- sanitized Scout observation upload after successful local measurements;
- shared player-history lookup by Torn user ID;
- local caching of successful global lookups;
- a local pending-sync queue for failed uploads;
- 30-minute duplicate suppression for materially identical observations;
- clear provenance labels such as `LIVE`, `LOCAL`, `GLOBAL`, and `HISTORICAL`;
- graceful failure when Google services are unavailable;
- tests for sanitization, validation, deduplication, queueing, and API-contract handling.

Out of scope for this v4.3 slice:

- private recruiter CRM sync;
- recruiter notes, contact history, salary negotiations, message contents, API keys, or authentication secrets in the Sheet;
- vacancy Match Scores;
- public editable Google Sheets;
- direct Google OAuth for every Recruitment Agency user;
- replacing local IndexedDB or the existing Scout cache/history;
- background scraping of Torn pages not actively viewed by the user.

## Data ownership and privacy boundary

Only sanitized Torn/player intelligence may leave the browser for the shared store.

Allowed global fields:

- `playerId`
- `name`
- `observedAt`
- `level`
- `ee`
- `activity30`
- `xanax30`
- `refills30`
- `attacks30`
- `rwHits30`
- `networth`
- `fit`
- `fitType`
- `lastActive`
- `scoutStatus`
- `sourceVersion`

Private/local-only information includes:

- Torn API key;
- recruiter notes;
- recruitment status and private CRM state;
- contact history and message contents;
- desired or negotiated pay entered by the recruiter;
- private role/availability notes;
- Google credentials or Apps Script deployment credentials.

The client must construct uploads from an explicit whitelist. It must never serialize a complete Scout, forum, settings, IndexedDB, or CRM object and then attempt to remove sensitive fields afterward.

## Google Sheet model

### Players

One row per Torn player containing the latest accepted global observation.

Columns:

`playerId | name | observedAt | level | ee | activity30 | xanax30 | refills30 | attacks30 | rwHits30 | networth | fit | fitType | lastActive | scoutStatus | sourceVersion | firstSeen | observationCount`

`playerId` is the logical unique key. The Apps Script updates the existing row when a newer accepted observation arrives.

### Observations

Append-only accepted historical measurements.

Columns:

`playerId | name | observedAt | level | ee | activity30 | xanax30 | refills30 | attacks30 | rwHits30 | networth | fit | fitType | lastActive | scoutStatus | sourceVersion`

Rows are treated as historical data, not recruiter decisions. Existing observation rows are not edited except for administrator repair/migration work.

### Meta

Small key/value configuration table.

Initial entries:

- `schemaVersion = 1`
- `serviceVersion = 4.3.0`
- `dedupeWindowMinutes = 30`

## Apps Script API

The Apps Script deployment runs as the Sheet owner and exposes the service through its `/exec` URL. The Sheet itself remains private.

### POST observation

Request body:

```json
{
  "action": "observe",
  "schema": 1,
  "player": {
    "id": 3877028,
    "name": "R4G3",
    "level": 52
  },
  "observation": {
    "observedAt": 1786788000000,
    "ee": 9,
    "activity30": 142,
    "xanax30": 61,
    "refills30": 27,
    "attacks30": 216,
    "rwHits30": 44,
    "networth": 2100000000,
    "fit": 86,
    "fitType": "official",
    "lastActive": 1786787700000,
    "scoutStatus": "fresh",
    "sourceVersion": "4.3.0"
  }
}
```

Successful response:

```json
{
  "ok": true,
  "accepted": true,
  "deduped": false,
  "playerId": 3877028,
  "observationCount": 4,
  "firstSeen": 1784000000000,
  "lastSeen": 1786788000000
}
```

A duplicate submission returns `ok: true`, `accepted: false`, `deduped: true` rather than being treated as an error.

### GET player history

Request:

`GET /exec?action=player&id=3877028`

Response:

```json
{
  "ok": true,
  "playerId": 3877028,
  "latest": {
    "name": "R4G3",
    "level": 52,
    "ee": 9,
    "activity30": 142,
    "fit": 86,
    "observedAt": 1786788000000
  },
  "history": [
    {
      "observedAt": 1786788000000,
      "activity30": 142,
      "fit": 86
    }
  ],
  "observationCount": 4,
  "firstSeen": 1784000000000,
  "lastSeen": 1786788000000
}
```

The service may cap returned history to a finite newest-first window so one popular player cannot create an unbounded response. The initial cap is 100 observations per player.

### Health/meta lookup

`GET /exec?action=meta`

Returns the current schema and service version so clients can disable incompatible global sync cleanly.

## Validation and abuse controls

Apps Script validates every request before writing.

Required controls:

- reject malformed JSON;
- reject unsupported schema versions;
- explicit allowed-field whitelist;
- reject unknown top-level actions;
- validate Torn player ID as a positive safe integer;
- cap player name length;
- validate numeric fields as finite, non-negative values where appropriate;
- constrain EE, level, Fit, counters, timestamps, and other fields to broad sanity ranges;
- reject timestamps too far in the future;
- cap request-body size;
- prevent formulas from being stored as executable formulas by writing values as plain text/numbers and neutralizing leading formula prefixes in strings;
- never allow the client to choose arbitrary Sheet names, ranges, formulas, or column indexes;
- use `LockService` around read-modify-write operations;
- use Apps Script cache/properties for lightweight rate limiting and service metadata;
- return JSON errors without Sheet internals or stack traces.

Global data is advisory. A malicious or inaccurate public submission must never overwrite a fresher direct Torn observation in the local UI.

## Deduplication

Before appending, the service compares the new sanitized measurement to the latest accepted observation for that player.

If the material measurement fields are equal and the newest observation is less than 30 minutes old, the service skips the append and returns a deduped success.

Material fields are:

`level, ee, activity30, xanax30, refills30, attacks30, rwHits30, networth, fit, fitType, lastActive`

Changes to `sourceVersion` or Scout freshness labels alone do not force another historical row.

A materially changed observation is accepted immediately even inside the 30-minute window.

## Client integration

The userscript receives a configurable Apps Script endpoint URL. The endpoint is not a secret and may be stored in project defaults/settings.

After a successful Scout measurement:

1. save the complete local Scout snapshot exactly as v4.2 already does;
2. construct a new sanitized global observation using an explicit field whitelist;
3. enqueue it locally for global sync;
4. attempt submission asynchronously without blocking normal Scout completion;
5. mark the queue item complete on accepted or deduped success;
6. retain it for a capped retry if the service is unavailable.

Global history lookup is performed when candidate history is requested or when the Results layer needs a shared-history enrichment. A recent local cache is reused before calling Apps Script again.

The client must not make global network traffic part of the Torn API scheduler because Apps Script calls are not Torn API calls. It must, however, have its own conservative concurrency and retry limits.

## Local storage

v4.3 adds local stores/records for global integration without deleting existing v4.2 data.

Recommended IndexedDB version: 10.

New stores:

- `globalLatest` keyed by `userId`, containing the newest fetched shared summary plus fetch timestamp;
- `globalHistory` keyed by a deterministic observation identity or composite snapshot ID for locally cached shared history;
- `globalSyncQueue` keyed by queue ID for pending sanitized uploads.

Existing stores remain unchanged:

- `users`
- `meta`
- `scoutLatest`
- `scoutHistory`

The upgrade is additive.

## Retry behavior

A global upload failure never turns a successful Torn Scout operation into a failed Scout operation.

Pending uploads use capped exponential retry metadata. Initial behavior:

- first retry after normal future Recruitment Agency activity rather than a tight background loop;
- maximum 5 failed automatic attempts per queued observation;
- accepted/deduped observations are removed from the queue;
- permanently invalid schema/data responses are removed and recorded as rejected rather than retried forever;
- a manual `Retry Global Sync` control may retry eligible queue entries.

No retry cadence is allowed to hammer Apps Script continuously while Torn is idle.

## Provenance and precedence

Displayed intelligence carries provenance.

Priority from strongest to weakest:

1. `LIVE` — fresh direct Torn/API state from the current operation;
2. `LOCAL` — current local Scout observation;
3. `GLOBAL` — recent shared observation from Google Sheets;
4. `HISTORICAL` — older shared observations;
5. parsed forum information.

Shared observations never silently replace fresher direct/local values. When both exist, history is used for comparison, trend context, first/last-seen metadata, and fallback only when the current field is unavailable.

## UI

v4.3 keeps the normal Results view compact.

Global intelligence appears as optional enrichment rather than another permanent wall of controls.

Initial UI additions:

- Global sync status indicator in Advanced Settings;
- Apps Script endpoint field in Advanced Settings;
- `Test Global Service` action;
- `Retry Global Sync` action when pending items exist;
- optional `Global` / `Historical` provenance badges in candidate details/history;
- shared first seen, last seen, observation count, previous Fit, previous Activity 30d, and deltas where available.

No private CRM notes or contact state are rendered from or sent to the global service.

## Google Sheet bootstrap

The project will include an Apps Script source file and setup documentation in the repository so the service is reproducible.

Repository additions are expected to include something equivalent to:

- `global/google-apps-script/Code.gs`
- `global/google-apps-script/README.md`
- `global/google-apps-script/schema.md`

The Google Sheet itself is created in the owner's Google Drive and initialized with the three required tabs and headers.

Deployment of Apps Script may require a one-time manual action in Google's Apps Script UI if the available automation tools cannot create/deploy an Apps Script project directly. The userscript integration must therefore support an unset endpoint and remain fully functional with global sync disabled until a valid endpoint is configured.

## Error handling

The global layer must fail open with respect to core Recruitment Agency functionality.

Examples:

- Apps Script timeout: keep local Scout result, queue sanitized upload, show non-blocking sync warning.
- HTTP/non-JSON failure: keep local data and queue upload.
- incompatible schema: disable automatic uploads until endpoint/schema is corrected; do not delete queued data.
- player lookup not found: treat as no shared history, not an application error.
- invalid global data: ignore the offending global fields/record rather than overriding local data.

## Testing

Add pure tests for:

- global observation whitelist/sanitization;
- omission of API key, notes, CRM/contact fields, and unrelated Scout fields;
- allowed numeric/null handling;
- material-observation equality used by client dedupe helpers;
- Apps Script response normalization;
- precedence rules between local and global values;
- pending-sync retry classification;
- IndexedDB/static migration to v10 and new additive stores;
- v4.3 version metadata;
- endpoint-disabled behavior;
- retention of the existing 75 Torn API calls/minute and 800 ms scheduler gap;
- continued absence of Recruit Scout paid/protected backend dependencies.

Apps Script source should also contain a testable validation layer or documented manual test vectors for valid observation, duplicate observation, invalid schema, invalid ID, oversized payload, and player lookup.

## Success criteria

v4.3 is successful when:

- a valid Scout observation remains fully stored locally and can also be sanitized and submitted to the configured Apps Script service;
- the same player can accumulate useful cross-user historical observations in Google Sheets;
- identical repeat observations inside 30 minutes do not create spam rows;
- another Recruitment Agency user can retrieve a player's shared history without Google authentication;
- no Torn API key or recruiter-private CRM/contact data appears in upload payloads or the global Sheet schema;
- Google service failure never breaks local scanning/scouting;
- shared data is visibly lower-priority than fresher direct/local Torn data;
- all existing v4.2 tests and safety constraints continue to pass.
