# Recruitment Agency v4.5 UI + Recruitment Workflow Design

## Status

Approved direction for v4.5. This document supplements and refines `docs/superpowers/specs/2026-08-15-forum-discovery-v4.5-design.md` and `docs/superpowers/specs/2026-08-16-approved-additions-lock.md`.

Where this document changes UI structure, navigation, layout, or presentation, this document is authoritative. Where it does not explicitly change behavior, the earlier v4.5 Forum Discovery design remains authoritative.

The visual direction is informed by screenshots supplied by the user from MoDuL's Pythagoras Project Python Edition. We may reuse interface ideas, hierarchy, workflows, component patterns, and visual principles. Recruitment Agency implementation remains clean-room and must not copy protected source code.

## Goal

Ship v4.5 as one coherent release that combines:

1. A major Recruitment Agency UI redesign with Pythagoras-level visual polish and consistency.
2. Forum Discovery for job seekers and explicit train buyers.
3. A unified local candidate database and six-stage recruitment pipeline.
4. Candidate messaging, source history, Scout integration, Smart Match integration, and resilient sync behavior.

The result should feel like a focused recruitment application rather than a collection of increasingly crowded controls.

## Core UX Principles

- One Torn player ID maps to one local candidate.
- Discovery, Candidates, Pipeline, Scout, Smart Match, and Global Intelligence remain distinct concepts but share one application shell.
- Navigation must scale to later versions without adding another row of top-level buttons.
- Tables remain dense and practical. Cards are optional, not mandatory.
- Green is an accent, not a flood-fill theme.
- Primary actions are visually obvious; destructive actions are visually isolated.
- Every major screen uses the same panel, spacing, title, form, table, status, and notification rules.
- Simple mode hides technical controls, not core recruiting capability.
- No UI action may silently change recruiter workflow state unless the action is itself an explicit workflow action.

## Application Shell

v4.5 replaces the current top-level mode-heavy layout with a collapsible left sidebar and a persistent page header.

### Sidebar

Desktop structure:

```text
RECRUITMENT AGENCY
v4.5

RECRUITMENT
  Overview
  Discover
  Candidates
  Pipeline

INTELLIGENCE
  Scout
  Smart Match
  Global Intelligence

APPLICATION
  Settings
  Data
  Logs
```

Requirements:

- Sidebar is visible by default on desktop.
- Sidebar can collapse to icon-only mode.
- Active page has a restrained accent outline/fill.
- Section headings are visually distinct but quiet.
- Sidebar collapse state is local and persisted.
- Narrow layouts use a slide-out sidebar while preserving the same navigation model.

### Persistent Page Header

Every page uses the same header structure:

```text
[Page title]                                  [status] [primary action] [secondary action]
```

Examples:

- Discover: status + `Sync Forum Posts`
- Candidates: status + `Refresh`
- Pipeline: status + `Add Candidate`
- Scout: status + `Scout`
- Settings: status only unless a section has an explicit save action

Temporary success/failure messages use local toast notifications instead of occupying the page header indefinitely.

## Visual Language

### Theme

Default dark palette:

- App background: near-black/charcoal.
- Sidebar: slightly distinct charcoal surface.
- Panels: dark neutral grey.
- Raised/interactive surfaces: slightly lighter grey.
- Borders: muted green-grey.
- Primary text: off-white.
- Secondary text: muted grey-green.
- Accent: restrained green.
- Primary action: brighter green.
- Warning: amber.
- Danger: muted red.

The UI avoids heavy neon glow. Green remains Recruitment Agency's identity but is used mainly for active states, primary actions, progress, successful states, and selected navigation.

### Shared Components

All major pages reuse the same component system:

- application header
- sidebar navigation
- page header
- panel container
- panel title + one-line description
- KPI/stat cards
- button variants: primary, secondary, warning, danger
- compact status pills
- form rows and two-column form grids
- compact data tables
- modals
- candidate detail drawer
- tooltips/contextual help
- toasts
- console/log panel
- progress bars
- collapsible settings sections

Inline SVG icons are preferred over emoji-like symbols.

## Responsive Rules

- Wide desktop: sidebar + two-column/three-column content grids where useful.
- Medium width: sidebar collapses; wide grids become two columns.
- Small width: sidebar becomes slide-out; form grids become one column.
- Candidate tables may horizontally scroll rather than destroying column readability.
- Pipeline becomes a 3x2 stage grid at medium widths.
- Pipeline becomes one selectable stage at a time on small widths.
- Candidate detail drawer becomes full-width on narrow screens.

## Forum Discovery Behavior

Behavior from the existing v4.5 Forum Discovery spec remains in force.

Initial sources:

- Looking for Work/company recruitment posts
- configured faction/company recruitment sources already used by Recruitment Agency
- explicit train buyers from configured marketplace/training thread
- manual candidate additions

Candidates deduplicate by Torn `userId`.

Repeated posts:

- update latest source when newer
- append deduplicated local source history
- may fill parser-derived fields conservatively
- never overwrite recruiter-entered manual fields
- never reset stage, note, expected salary, or availability override

## Conservative Forum Parsing

Pure parsing recognizes only explicit evidence such as:

- looking for work/company
- explicit company type
- explicit company stars such as `10* AN`
- buying trains / looking to buy trains
- explicit train amount/range
- explicit primary work stat
- explicit availability

Ambiguous values remain unknown.

No generated inference may be persisted as fact without explicit supporting text.

## Safe Continuation and Checkpointing

Persisted Torn continuation is sanitized and validated.

Requirements:

- host must be `api.torn.com`
- path must be a supported `/v2/` path
- remove API `key`
- remove `comment`
- reject unsupported/malformed URLs

Per-page commit order:

```text
fetch through shared scheduler
validate page/posts
persist forumSources
merge candidateLocal
persist counters
persist sanitized next cursor LAST
continue
```

The cursor is stored only after the candidate/source writes for that page have completed.

Cancellation or failure preserves completed imports and the last safe checkpoint.

UI displays only a friendly continuation state such as `Resume available`, never the raw continuation URL.

## Fill Companies

Visible, cancelable operation.

Requirements:

- uses shared Torn scheduler
- shows checked X/Y progress
- records per-candidate failures
- partial successes remain stored
- does not change pipeline stage
- does not overwrite recruiter fields

## Message Player

Recruitment Agency never auto-submits Torn mail.

Message Player opens an in-app modal with:

- candidate identity
- prepared message editor
- `Edit`
- `Save as Default`
- `Copy & Open Torn Message`
- `Cancel`

Initial supported placeholders remain:

- `{name}`
- `{player_id}`
- `{looking_for}`
- `{company_name}`
- `{current_company}`
- `{match_score}`
- `{fit_score}`

Unknown values are removed cleanly.

Opening the Torn compose screen does not set the candidate to Contacted.

Clipboard failure leaves the prepared text visible/selectable and does not lose the message.

## Local Notifications

v4.5 adds in-app toast notifications for short-lived operational feedback, for example:

- candidates imported
- checkpoint preserved
- candidate moved to stage
- message copied
- Scout complete
- sync failure

These are not browser/system notifications.

Persistent or actionable failures also appear inside the relevant panel.

## Data Model

IndexedDB upgrades additively from v11 to v12.

### candidateLocal

Extend the existing v4.4 record with:

- pipelineStage
- availability
- expectedSalary
- recruiterNote
- latestForumSourceId
- discoverySources
- createdAt
- updatedAt

Existing v4.4 fields and manual precedence remain intact.

### forumSources

Key path: `sourceId`.

Indexes:

- userId
- postedAt
- sourceType
- threadId

Stores local source observations including post text/excerpt and parser-derived fields.

### forumSyncState

Key path: `feedId`.

Stores:

- configured source/thread identity
- last safe checkpoint
- sanitized continuation
- last sync metadata
- counters

Never stores the Torn API key.

### Additive Upgrade Rule

- no existing store is deleted
- `deleteObjectStore` is forbidden
- existing Scout/Results/Global/Match data remains compatible

## Candidate View Model

The UI composes one candidate view from:

```text
candidateLocal
+ latest forum source
+ existing discovery/user data
+ Scout latest/history summary
+ allowed Global Intelligence
+ Smart Match evaluation
```

Manual recruiter fields outrank parser-derived values.

Live/local intelligence outranks Global/Historical according to the existing provenance rules.

## Privacy Boundary

The following remain local and must never enter Global Intelligence:

- forum post text/excerpts
- forum post URLs/history
- pipeline stage
- availability override
- expected salary
- recruiter notes
- Default Recruitment Message
- prepared message text/editor state
- discovery source history
- private workflow state
- Match Score/Profile data

The v4.3 Global Intelligence whitelist remains exactly:

`playerId,name,observedAt,level,ee,activity30,xanax30,refills30,attacks30,rwHits30,networth,fit,fitType,lastActive,scoutStatus,sourceVersion`

## API and Security Constraints

- official Torn API only for supported API operations
- shared scheduler only
- hard maximum 75 calls/minute
- minimum 800 ms request gap
- no protected Recruit Scout backend
- no captcha/session bypass
- no unseen-page background scraping
- no automatic message submission
- no automatic pipeline advancement from opening links/composers

## Implementation Boundaries

Keep existing pure cores:

- `src/scout-core.js`
- `src/results-core.js`
- `src/global-core.js`
- `src/match-core.js`

Add pure v4.5 logic in:

- `src/forum-core.js`

`forum-core.js` owns testable pure behavior such as:

- source normalization
- source ID generation/deduplication
- forum-intent parsing
- train buyer parsing
- company/stars parsing
- availability parsing
- candidate/source merge precedence
- six-stage validation
- message placeholder substitution
- safe continuation normalization

The userscript remains responsible for:

- DOM/UI shell
- IndexedDB integration
- shared scheduler integration
- page rendering
- context menus/drawers/modals
- Torn navigation/opening links

Targeted extraction of reusable UI helpers is allowed if it reduces the userscript's complexity, but v4.5 must not become a framework rewrite.

## Non-Goals for v4.5

- multiple named message templates
- AI-written recruiting messages
- automatic Torn message send
- automatic pipeline progression
- cloud/shared recruiter CRM
- global forum post sharing
- v4.6 conversion analytics
- full workspace backup/import product
- a Pythagoras source-code port

## Success Criteria

v4.5 is complete when:

1. The interface has the new sidebar/page/panel visual system and remains usable on smaller widths.
2. All previously approved Forum Discovery and Candidate Pipeline behavior is implemented.
3. Candidates is the primary authoritative recruitment table, with no competing candidate database.
4. Pipeline, Scout, Smart Match, Global Intelligence, Settings, Data, and Logs share the same coherent application shell.
5. Forum sync is resumable, safe, scheduler-controlled, and local-first.
6. Recruiter-private data remains local.
7. Messaging remains human-send only.
8. The full test and syntax suite is green.
9. The feature branch is merged to GitHub `main` only after post-merge CI passes.
