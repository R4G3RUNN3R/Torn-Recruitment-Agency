# v4.6 Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish the storage, domain-boundary, migration, and collapsible-navigation foundation required for separate Company and Faction recruitment while preserving one shared Player Intelligence identity per Torn ID.

**Architecture:** Add three focused v4.6 modules rather than expanding the already-large `v45-app.js`: a pure domain module, an additive DB13/repository module, and a navigation-state module. The Foundation PR introduces the new internal architecture without becoming the public v4.6 release: the public `R4G3RUNN3R-Recruitment-Agency.user.js` remains the reviewed immutable v4.5.4 bootstrap until a complete user-facing Company/Faction slice is ready. Legacy recruitment data is classified by provenance rather than blindly treated as Company data, and shared Player Intelligence accepts only explicit player-fact fields so recruitment-private state cannot leak into the shared record.

**Tech Stack:** Plain JavaScript UMD/CommonJS userscript modules, IndexedDB, Node `node:test`, `fake-indexeddb`, JSDOM, Puppeteer/Chromium, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-24-v4.6-recruitment-platform-architecture-design.md`

## Global Constraints

- One Torn ID = one authoritative shared Player Intelligence identity.
- Company Recruitment and Faction Recruitment are separate domains.
- Company pipeline state, notes, salary, tags, follow-ups, campaigns and outcomes must never populate Faction state or shared Player Intelligence.
- Faction pipeline state, notes, waivers, specialist state, tags, follow-ups, campaigns and outcomes must never populate Company state or shared Player Intelligence.
- Shared Scout/player observations update the player once; Company/Faction conclusions remain domain-specific.
- A discovery creates recruitment state only in its own domain.
- No automatic or bulk Torn message sending.
- Maximum 75 Torn API calls/minute and minimum 800 ms spacing remain unchanged.
- All Torn API requests continue through the existing shared scheduler.
- Database migration is additive only; never call `deleteObjectStore()` and never reset DB12 data to introduce DB13.
- Existing DB12 stores remain readable after DB13 migration.
- The Global Intelligence whitelist remains unchanged.
- Settings remains title-bar-only; no duplicate sidebar Settings entry.
- Preserve v4.5.4 internal scrolling, Maximize/Restore, hostile-click shielding, mobile behavior, launcher behavior, and geometry persistence.
- Do not silently reorder the current runtime Company pipeline during Foundation work.
- Do not expose dead Faction, Workforce, Analytics, Vacancies, Requirements, Today, Follow-ups, or other unbuilt architecture tabs.
- Do not change the public userscript metadata version, immutable `@require` pins, `INSTALLER_VERSION`, or `EXPECTED_APP_VERSION` in this Foundation PR.

- [ ] **Step 3: Implement the shared-field whitelist and normalizers**

Create `src/v46-domain-core.js` in the repository's UMD/CommonJS style. Define the only patch fields that may enter shared intelligence:

```js
const SHARED_PLAYER_FIELDS = Object.freeze([
  'name','level','ee','factionId','factionName',
  'currentCompany','currentCompanyId','currentCompanyRating','currentCompanyPosition','companyCheckedAt',
  'networth','fit','fitType','lastActive','lastScoutAt','lastGlobalAt',
  'activity30','xanax30','refills30','attacks30','rwHits30','scoutStatus'
]);
```

`mergePlayerIntelligence()` must copy only those fields from `patch`. It owns `userId`, `sources`, `nameHistory`, `createdAt`, and `updatedAt`; callers cannot inject those bookkeeping fields through the generic patch. Shared timestamps use numeric milliseconds.

Use this structure:

```js
function normalizeUserId(value) {
  const userId=String(value??'').trim();
  if(!/^\d+$/.test(userId)||Number(userId)<=0) throw new Error('A valid Torn player ID is required.');
  return userId;
}

function mergePlayerIntelligence(existing,patch={},source='unknown',observedAt=Date.now()) {
  const at=Number.isFinite(Number(observedAt))?Number(observedAt):Date.now();
  const userId=normalizeUserId(patch.userId??existing?.userId);
  const next={...(existing||{}),userId};
  for(const key of SHARED_PLAYER_FIELDS) if(Object.hasOwn(patch,key)) next[key]=patch[key];
  const label=String(source||'unknown').trim()||'unknown';
  next.sources=[...new Set([...(Array.isArray(existing?.sources)?existing.sources:[]),label])];
  next.createdAt=Number(existing?.createdAt||at);
  next.updatedAt=Math.max(Number(existing?.updatedAt||0),at);
  const name=String(next.name||'').trim();
  const history=Array.isArray(existing?.nameHistory)?existing.nameHistory.map(x=>({...x})):[];
  if(name && history.at(-1)?.name!==name) history.push({name,observedAt:at});
  next.nameHistory=history;
  return next;
}
```

Define accepted Company stage values without changing their live order. Define Faction stages as `Prospect, Contacted, Replied, Evaluating, Invite Ready, Joined, Rejected, Deferred`.

Legacy faction stage mapping is exactly:

```js
const LEGACY_TO_FACTION_STAGE=Object.freeze({
  'Not Contacted':'Prospect',
  'Shortlisted':'Evaluating',
  'Contacted':'Contacted',
  'Replied':'Replied',

  'Rejected':'Rejected'
```

`classifyLegacyDomains()` treats `COMPANY FORUM`, `TRAIN BUYER`, and `MANUAL` as Company evidence and `FACTION FORUM` as Faction evidence. It checks both `candidate.discoverySources` and matching `forumSources`. With no evidence, return `['company']` and let conversion set `legacyDomainAssumed:'company'`.

For `options.ambiguous===true`, both converters preserve the original `pipelineStage`, `availability`, `recruiterNote`, and recruitment-facing fields inside `legacySharedState`, set `migrationReviewRequired:true`, and use safe default stages (`Not Contacted` for Company, `Prospect` for Faction) rather than inventing which old workflow the shared state referred to.

```js
function legacyTimestamp(value,fallback){
```
