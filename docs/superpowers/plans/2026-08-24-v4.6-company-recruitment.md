# v4.6 Company Recruitment Expansion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the first complete Company Recruitment slice on top of the merged DB13 Foundation, with dedicated Company routes, baseline eligibility, vacancies, operational queues, campaigns/follow-ups/history, and domain-safe persistence while keeping the public v4.5.4 installer pinned until release hardening.

**Architecture:** Add a DB14 additive layer for reusable Company entities while keeping one `companyRecruitment` record per Torn player and one shared `playerIntelligence` identity. Put Company calculations and operational transformations in focused v4.6 modules, then let `v45-app.js` act only as shell/controller glue. No Company action may create or mutate Faction recruitment state.

**Tech Stack:** JavaScript userscript modules, IndexedDB, Node test runner, JSDOM, Puppeteer/Chromium, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-24-v4.6-recruitment-platform-architecture-design.md`

## Global Constraints

- One Torn ID = one authoritative shared Player Intelligence identity.
- Company Recruitment and Faction Recruitment remain separate domains.
- Torn API ceiling remains 75 requests/minute with at least 800 ms between Recruitment Agency Torn API calls.
- Smart/local calculations must not create Torn API calls.
- Torn messages remain manual-send only.
- Global Intelligence whitelist remains exactly unchanged.
- Database upgrades remain additive; no object store deletion.
- Opening profile/forum/message compose never changes stage.
- Public `R4G3RUNN3R-Recruitment-Agency.user.js` stays v4.5.4 with current immutable pins until separate release hardening.
- Existing runtime pipeline ordering discrepancy is not silently changed in this slice.
